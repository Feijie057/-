# 平台组成方式分析与工作台设计

## 0. 一个必须先说明的前提

本次任务要求先分析 `https://projectnvwa.ai/`。**该站点在本工作环境中无法访问**：

- `curl https://projectnvwa.ai/` → `CONNECT tunnel failed, response 403`
- 代理状态接口记录：`{"kind":"connect_rejected","host":"projectnvwa.ai:443"}`
- 同一策略下 `example.com` 同样被拒，说明是环境级出网限制，不是该域名本身的问题
- 搜索引擎未收录该站点，检索到的只有同名的其他项目（微软 NÜWA 视觉生成模型、久其女娲平台、女娲智能体 OS 等），无法据此推断

因此，**下文的「平台组成」不是对该站点的还原，而是按用户确认的定位（AI 内容生成平台，
「输入需求 → 平台内部一套运作逻辑 → 产出内容」）给出的通用组成模型**，本仓库的工作台按此实现。
拿到真实页面内容（文案 / 截图 / HTML）后，替换第 2 节的模块清单与第 4 节的配方即可对齐。

## 1. 这类平台的本质：一条可复用的转换链

AI 内容生成平台看上去是「聊天框 + 模型」，实际的价值不在模型调用，而在**把一次性的对话固化成可重复执行的转换链**：

```
需求(Brief) ──▶ 配方(Recipe) ──▶ 流水线执行(Job) ──▶ 产出物(Artifact)
                    ▲                  │
                    │                  ▼
              品牌资产(Assets)     运行记录(可回溯)
```

四个名词构成整个平台的数据骨架，缺一个就会退化：

| 缺失 | 退化成什么 |
| --- | --- |
| 缺配方 | 退化成一个聊天框，每次都要重新描述要求 |
| 缺品牌资产 | 每次产出的语气、术语都不一致，需要人工统一 |
| 缺运行记录 | 产出是黑箱，出了问题不知道是哪一步坏的 |
| 缺产出库 | 内容散落在各处，无法复用与二次加工 |

## 2. 模块组成（八个模块，四层）

| 层 | 模块 | 职责 | 本仓库实现 |
| --- | --- | --- | --- |
| 入口层 | **工作台总览** | 讲清平台主张，给出量化状态与快捷入口 | `src/pages/Dashboard.tsx` |
| 生产层 | **创作台** | 三栏：填需求 / 看流水线 / 取产出 | `src/pages/Studio.tsx` |
| 生产层 | **配方库** | 定义与编辑「运作逻辑」本身 | `src/pages/Recipes.tsx` |
| 生产层 | **产出库** | 成品归档、检索、收藏、导出 | `src/pages/Library.tsx` |
| 供给层 | **品牌资产** | 作为长期上下文注入每一步 | `src/pages/Assets.tsx` |
| 供给层 | **模型接入** | 多服务商配置与连通性自检 | `src/pages/Models.tsx` |
| 运维层 | **运行记录** | 逐步回看中间产物，定位问题环节 | `src/pages/Jobs.tsx` |
| 运维层 | **设置** | 主题、导入导出、清理 | `src/pages/Settings.tsx` |

## 3. 核心机制：流水线执行器

平台的「运作逻辑」被实现为一个顺序执行器（`src/lib/engine.ts`）：

1. 用品牌资产拼出 system prompt，注入每一步；
2. 按配方定义逐步执行，每步用 `renderTemplate` 把 `{{字段}}`（取自需求表单）和
   `{{steps.步骤id}}`（取自前序步骤输出）填入提示词；
3. 流式回传 token，UI 实时追加；
4. 任一步失败则后续步骤标记为 `skipped` 而非 `failed`——失败原因只有一个，不会被连锁噪音淹没；
5. 最后一个 `format` 步骤的输出即成品。

六种步骤语义（也是平台对用户讲述自己的方式）：

| 语义 | 作用 |
| --- | --- |
| 拆解 `plan` | 把需求翻译成可执行的内容策略 |
| 调取 `retrieve` | 从品牌资产与参考资料中取上下文 |
| 生成 `generate` | 产出内容主体 |
| 润色 `refine` | 压缩冗余、强化表达 |
| 校验 `validate` | 合规、事实与逻辑自检 |
| 成品 `format` | 排版并打包为可交付物 |

**把校验放进流水线而不是放在交付前**，是这类平台区别于「聊天框」最实际的一点：
合规问题在产出之前就被拦截，改动成本最低。

## 4. 内置配方（六条）

| 配方 | 步骤数 | 产出 |
| --- | --- | --- |
| 小红书种草笔记 | 6 | 标题 × 5、正文、话题标签、配图脚本 |
| 公众号深度长文 | 6 | 提纲、正文、导语与摘要 |
| 短视频口播脚本 | 5 | 分镜表、口播词、字幕 |
| 电商详情页文案 | 6 | 主图文案、卖点模块、FAQ、规格表 |
| 品牌命名与 Slogan | 5 | 命名候选、Slogan、品牌故事 |
| 一稿多投改写 | 5 | 各平台版本、差异说明 |

配方是数据不是代码：内置配方只读，可「复制后编辑」，也可从零新建。

## 5. 模型适配层

`src/lib/providers.ts` 用同一个 `generate()` 接口抹平三种来源：

| 类型 | 说明 |
| --- | --- |
| `mock` | 本地模拟引擎，离线可完整跑通流程，输出形状与真实一致 |
| `anthropic` | 直连 Messages API，SSE 流式 |
| `openai` | 任何兼容 `/chat/completions` 的服务 |

默认使用模拟引擎，因此**不配置任何密钥就能完整演示「输入 → 运作 → 产出」**。

## 6. 已知边界

- 密钥保存在浏览器 `localStorage`，仅适合本地与内网演示；生产环境应改为后端代理转发，前端不接触密钥。
- 浏览器直连模型服务受 CORS 限制，部分服务商需要自建代理。
- 数据全部存在 `localStorage`，清缓存即丢失；设置页提供导出/导入作为迁移手段。
- 流水线目前是顺序执行，不支持分支与并行。分支能力应加在 `engine.ts` 的步骤循环处，而不是散在各配方里。
